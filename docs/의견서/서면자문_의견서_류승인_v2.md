# 사전기획 검토 업무 AI 전환을 위한 서면자문 의견서

**자문위원**: 류승인 | 서울특별시 광진구청 주무관 (2020~)

**작성일자**: 2026. 3. 20.

---

광진구청에서 6년째 행정 업무를 하고 있습니다. 전산학을 전공한 적 없는 행정직 공무원인데, 틈틈이 독학으로 코딩을 익혀 지난 10개월간 22개의 실무 프로젝트를 직접 만들고 배포했습니다. 같은 공공기관에서 같은 고민을 먼저 해본 사람으로서, 솔직하게 말씀드리겠습니다.

---

## 1. '내부 역량 중심 애자일 방식' AI 전환 추진방향의 적절성

내부 역량 중심의 애자일 방식을 강력히 지지합니다. 단순한 선호가 아닙니다. 제가 직접 걸어온 길이기 때문입니다.

지금 AI 시대에 가장 큰 변화는, 전문 개발자가 아닌 현장의 도메인 전문가가 직접 문제를 해결할 수 있게 되었다는 겁니다. NVIDIA 젠슨 황은 "이제 모든 사람이 프로그래머"라고 했고, 전 하버드 컴퓨터과학 교수이자 구글 엔지니어링 리드였던 Matt Welsh는 ACM에 「프로그래밍의 종말」이라는 글을 기고하면서, AI가 작업 설명만으로 소프트웨어를 만들어내는 시대를 예측했습니다.

이론이 아닙니다. 올해 2월 Anthropic 해커톤에서 13,000명이 지원하고 277팀이 겨뤘는데, 주요 수상자 5명 중 4명이 비개발자였습니다. 금상은 상해 전문 변호사, 은상은 심장내과 의사, 동상은 뮤지션. 전문 개발자는 딱 1명이었습니다. 국내에서도 작년 바이브코딩 해커톤에서 비전공자들이 4시간 만에 서비스를 완성한 사례가 있습니다.

저도 마찬가지입니다. 행정학 전공 공무원이 10개월 만에 법령 분석 플랫폼, 문서 전문검색 앱, MCP 서버를 만들 수 있었던 건 — 현장에서 매일 부딪히는 문제를 누구보다 잘 알았기 때문입니다.

용역 업체는 우리 업무를 모릅니다. 요구사항 전달, 개발, 검수, 수정 요청… 그 긴 사이클 동안 현장의 요구는 벌써 바뀌어 있습니다. 업무 담당자가 직접 만들면 아침에 떠오른 아이디어를 점심때 프로토타입으로 돌려볼 수 있습니다.

물론 내부 개발이 만능은 아닙니다. 대규모 시스템이나 보안이 극도로 중요한 인프라는 전문 업체가 필요합니다. 하지만 업무 보조 도구, 데이터 전처리, 분석 자동화 같은 영역은 도메인 전문가가 AI와 함께 직접 만드는 게 예산, 속도, 품질 모든 면에서 낫다고 확신합니다.

## 2. MVP 1~3 모델의 기술적 타당성 및 고도화

솔직한 감상부터 말씀드리면, 코딩 입문자 단계에서 이 정도 파이프라인을 설계하고 작동시킨 것 자체가 대단합니다. 실무 문제를 정확히 짚었고, 방향도 옳습니다. 코드를 살펴보니 몇 가지만 개선하면 훨씬 안정적인 도구가 될 수 있어서, 구체적으로 짚어 드리겠습니다.

### MVP 1 (이미지 → AI 친화적 변환)

**잘된 점**: 병렬 처리(ThreadPoolExecutor)로 대량 문서를 빠르게 돌리는 구조, 지수 백오프 재시도, 이미 처리된 페이지를 건너뛰는 '이어하기' 기능 — 프로덕션 수준에 근접한 설계입니다.

**개선 포인트**:

첫째, `main.py`에 2단계(OCR)가 절대 실행되지 않는 버그가 있습니다. `return` 문 뒤에 `time.sleep(2)`가 와서 1단계 성공 후에도 2단계로 넘어가질 못합니다. 들여쓰기 한 단계만 빼면 해결되는데, 작은 실수가 프로그램 전체 흐름을 막고 있으니 가장 먼저 잡으시길 권합니다.

둘째, `ai_ocr.py` 예외 처리에서 구체적인 API 오류 4가지를 나열해 놓고 마지막에 `Exception`을 함께 잡아서, 앞의 4개가 사실상 의미가 없어졌습니다. API 일시 오류만 재시도하고 프로그래밍 오류는 즉시 멈추게 하는 게 디버깅에 유리합니다.

셋째, PDF를 이미지로 바꿀 때 전체 페이지를 한꺼번에 메모리에 올립니다. 수백 페이지짜리를 돌리면 메모리가 터질 수 있으니 `first_page`/`last_page`로 20~30페이지씩 끊어 처리하길 권합니다.

### MVP 2 (페이지 발췌 + 라벨링)

3종 중 완성도가 가장 높습니다. 외부 API 없이 오프라인에서 끝나고, PdfReader 캐싱이나 `copy.copy` 원본 보호 같은 세심한 부분도 잘 되어 있습니다.

다만 `except:`(빈 예외 처리)가 몇 군데 있어서 Ctrl+C로 프로그램 종료가 안 되는 문제가 생깁니다. `except Exception:`으로 바꾸면 해결됩니다. `TOPIC_FOLDERS`나 `SOURCE_FILES` 같은 설정값도 별도 파일(YAML 등)로 빼면 재사용이 편해집니다.

### MVP 3 (교육과정 분석)

2단계 요약(개별 파일 → 통합 분석)은 대량 문서 분석의 정석이고, 'Architect-Collaborator' 페르소나 프롬프트도 잘 설계되어 있습니다.

한 가지. 1단계에서 일부 파일 요약이 실패하면 그 데이터가 2단계에서 빠지는데, "10개 중 7개만 성공했다"는 안내가 없습니다. 불완전한 분석을 완전한 것으로 오인할 수 있으니 성공/실패 카운트를 최종 리포트에 넣으시길 권합니다.

### 공통 개선 방향

세 MVP 모두 가장 큰 개선점은 설정의 외부화입니다. 경로, 모델명, 워커 수가 코드 안에 박혀 있어서 다른 PC에서 실행하려면 코드를 열어야 합니다. YAML 설정 파일 하나로 분리하면 해결됩니다. 콘솔에만 나오는 로그도 파일로 남기면 문제 추적과 성과 보고에 쓸 수 있습니다.

이런 개선을 반영한 구현체(실행 파일 포함)를 별첨으로 드립니다. 핵심 기능은 그대로 유지하면서 설정 외부화, 모듈화, 에러 처리 강화를 적용한 버전입니다.

## 3. 자생적 개발의 실현 가능 수준 및 예상 훈련기간

세 가지 기능의 난이도와 현실적 기간을 말씀드리겠습니다.

**RAG 구축** (검토 의견서 DB화 + AI 검색): 비유하자면 '오픈북 시험'입니다. AI가 자기 기억에만 의존하지 않고, 준비해 둔 문서를 먼저 찾아본 뒤 답변하는 방식이죠. 진입 장벽이 가장 낮고 도구(LangChain, LlamaIndex 등)도 잘 갖춰져 있어서 본업 병행 기준 2~4개월이면 기본적인 검색·답변 시스템을 만들 수 있습니다. 환각 방지는 출처 표시(어느 문서 몇 페이지인지)를 함께 보여주는 게 가장 효과적입니다.

**MCP 개발** (외부 데이터 연동): 쉽게 말해 'AI 세계의 USB-C'입니다. 예전에 기기마다 충전 단자가 달랐듯 AI가 외부 시스템에 접속하려면 매번 별도 코드를 짜야 했는데, MCP라는 표준 규격 덕에 한 번 만들면 어디서든 연결됩니다. 제가 국가법령정보시스템 API용 MCP 서버(64개 도구)를 만들어 오픈소스로 공개한 경험이 있는데, RAG보다 한 단계 어렵지만 3~6개월이면 기본 서버 구축이 가능합니다.

**AI 에이전트** (검토의견서 초안 도출 등): '자율 행동하는 비서'입니다. 질문에 답하는 데 그치지 않고 스스로 자료를 찾고 판단하고 실행까지 합니다. 가장 복잡한 단계로 6개월에서 1년 정도 잡아야 합니다. 다만 RAG와 MCP를 먼저 거치면 자연스럽게 도달하는 단계이니 순서대로 가시면 됩니다.

## 4. AI 전환 추진 시 장애요인과 해결책

### 심리적 장벽: '다 알아야 한다'는 강박

가장 먼저 마주치는 벽은 두려움입니다. "프로그래밍을 제대로 배워야 할 것 같은데…" "프론트엔드가 뭔지 백엔드가 뭔지도 모르는데…" 이 생각이 첫 걸음을 막습니다.

솔직히 고백합니다. 저도 22개 프로젝트를 만들었지만 프로그래밍의 세부적인 것까지 다 알지 못합니다. 그런데도 법령 분석 플랫폼, 문서 검색 앱, 소식지 자동 생성 시스템을 매일 실무에서 돌리고 있습니다. AI가 코드를 써주니까요.

'바이브 코딩'이라는 말을 만든 안드레이 카파시(OpenAI 공동창업자, 전 Tesla AI 총괄)가 이렇게 정의했습니다 — "코드가 존재한다는 사실조차 잊고, 완전히 바이브에 몸을 맡기는 것." 코드를 모르는 게 문제가 아닙니다. AI 시대에는 코드를 신경 쓰지 않아도 됩니다.

처음부터 "프로그래밍을 배운다"고 접근하지 마십시오. "내 업무에서 귀찮은 걸 AI한테 시켜본다"로 시작하면 됩니다. 그러다 보면 코드도 자연스럽게 읽히기 시작합니다.

### 구조적 장벽: 조직의 변화는 위에서 시작해야 합니다

심리적 두려움보다 더 깊은 문제가 있습니다. 동기부여입니다.

아래에서부터 올라오는 바텀업 방식으로 AI를 퍼뜨리는 건, 구조적으로 한계가 뚜렷합니다. 이유는 단순합니다. AI를 열심히 배워서 업무에 적용한 사람과, 아무것도 안 한 사람 사이에 아무런 차이가 없기 때문입니다.

월급이 오르지 않습니다. 승진에 반영되지 않습니다. 어떤 혜택도 없습니다. 오히려 AI를 잘 쓰면 "너 좀 잘하네?" 소리와 함께 일만 더 늘어납니다. 그 구조에서 누가 퇴근 후에 새로운 걸 배우려 하겠습니까. AI 쓰면 내 일만 많아지는데.

위에서 내려오는 물결은 다릅니다.

"AI를 활용한 업무 개선 실적을 인사 평가에 반영하겠다." "AI 역량을 갖춘 직원에게 교육 기회와 보직 우대를 주겠다." 이런 신호가 위에서 떨어지는 순간, 사람들은 알아서 움직이기 시작합니다. 시키지 않아도 찾아 배우고, 자기 업무에 적용해 보고, 옆자리 동료한테 물어봅니다.

불씨를 지피는 건 아래에서도 할 수 있습니다. 하지만 그 불이 번지려면 바람이 필요합니다. 바람은 위에서 불어야 합니다.

지금 정부가 추진하는 국가 AX(AI 대전환)도 같은 맥락입니다. 대통령실에서 전략을 선언하고, 10.1조 예산을 편성하고, 공공기관에 AI 도입을 독려하는 건 — 현장 공무원 몇 명이 "AI 좋습니다"라고 외쳐서 되는 일이 아니었기 때문입니다. 위에서 방향을 잡고, 제도를 만들고, 자원을 배분해야 아래가 움직입니다.

제 경험도 그렇습니다. 개인의 호기심으로 여기까지 왔지만, 솔직히 이건 예외적인 케이스입니다. 조직 전체가 바뀌려면 개인의 열정에 기대선 안 됩니다. 열정은 소모됩니다. 제도는 지속됩니다.

그래서 제안드립니다. AI 역량을 갖춘 직원이 실질적으로 인정받는 구조를 먼저 만드십시오. 인사 가점이든 전문직위 지정이든 성과급 반영이든, 형태는 상관없습니다. "AI를 쓰면 나에게 좋은 일이 생긴다"는 신호가 명확해지는 순간, 교육 프로그램 없이도 사람들이 스스로 움직이기 시작할 겁니다.

## 5. 최적의 '바이브 코딩 툴' 추천

Claude Code를 추천합니다.

지금 주요 바이브 코딩 도구들(Cursor, GitHub Copilot, Windsurf 등)은 '코드 편집기 안에서 AI가 보조하는' 방식입니다. Claude Code는 다릅니다. AI가 직접 코드를 읽고, 수정하고, 실행하고, 테스트까지 합니다. 이 차이가 결정적입니다. 입문자한테는 편집기 다루는 법부터 배워야 하는 전자보다, 말로 지시하면 알아서 해주는 후자가 문턱이 훨씬 낮습니다.

22개 프로젝트를 만든 것도 Claude Code 덕분입니다. Rust 데스크톱 앱부터 Next.js 웹 플랫폼, MCP 서버까지 하나의 도구로 모든 기술 스택을 다뤘습니다.

윈도우 환경 걱정이 있으실 텐데, 저도 전부 윈도우에서 했습니다. Git Bash나 WSL(Windows에서 리눅스를 쓸 수 있게 해주는 기능)을 쓰면 문제없고, 이 초기 세팅도 AI가 도와줍니다. 공공기관 업무 환경이 윈도우라면 윈도우에서 개발하는 게 오히려 맞습니다.

**인프라 규모**: Claude Code 구독(월 $20~100, 사용량 따라), Gemini API 크레딧(계획대로 300 USD면 충분), 팀원 수에 따른 추가 구독. Anthropic이 올해 초 서울에 한국 사무소를 열 예정이어서 공공기관 지원이 확대될 가능성도 있습니다.

## 6. 정보 보안 및 LLM 윤리

보안은 반드시 지켜야 합니다. 동시에, 보안에 대한 막연한 두려움이 혁신을 막아서도 안 됩니다.

기준은 국정원이 2025년 12월에 발표한 「AI 보안 가이드라인」입니다. 15개 위협과 30개 대책을 1:1 매칭해 놓았고, 핵심은 셋 — 신뢰할 수 있는 출처의 데이터만 쓸 것, 개인정보·민감정보 사전 검사, 접근 통제 및 로깅.

더 큰 변화가 있습니다. 19년간 이어온 획일적 물리적 망분리가, 업무 중요도에 따른 3등급(기밀·민감·공개) 차등 보안으로 바뀌었습니다. 국가망보안체계(N2SF) 전환입니다. 공공기관에서도 AI와 클라우드를 쓸 수 있는 길이 열린 겁니다.

현장 경험을 솔직히 말씀드리면, 공직 6년 동안 정말 비공개해야 할 문서가 얼마나 됐나 돌아보면 손에 꼽습니다. 개인정보가 든 민원 서류, 감사 관련 내부 문서 정도. 사전기획팀에서 다루시는 법령, 지침, 서식, 교육과정 등은 대부분 이미 공개된 행정 데이터입니다.

물론 주의는 필요합니다. 개인정보보호위원회의 「생성형 AI 개인정보 처리 안내서」(2025. 8.)에 따라 AI에 데이터를 넣기 전 개인정보를 마스킹하는 전처리만 거치면 됩니다. 비정형 데이터 가명처리 기준도 2024년에 나왔으니 가이드라인을 따르면 법적으로 안전합니다.

서울시가 29개 생성형 AI 모델을 업무에 개방한 것, 전국 110개 이상 공공기관이 AI 도입 계약을 맺은 것 — 이 흐름이 말해줍니다. 보안 가이드라인을 지키면서 적극 활용하시길 권합니다.

## 7. 추가 제언

### 인터넷 창 속 AI와 '바이브 코딩'은 다릅니다

많은 분들이 ChatGPT나 Claude 웹 대화창에서 질문하고 답 받는 것을 'AI 활용'이라 생각합니다. 맞는 말이지만, 한계가 분명합니다. 대화창의 AI는 우리 컴퓨터 파일을 못 읽고, 코드를 못 돌리고, 결과를 못 확인합니다. 복사-붙여넣기는 전부 사람 몫입니다.

바이브 코딩은 다릅니다. AI가 직접 파일을 읽고, 코드를 쓰고, 실행하고, 오류나면 스스로 고칩니다. 사람은 방향만 잡아주면 됩니다. 이게 '에이전트 AI'이고, 지금 전 세계 AI 기업들이 여기로 달리고 있습니다.

### AI는 '확률 계산기'입니다

카카오톡에서 "오늘 점심"이라고 치면 자동완성이 "뭐 먹을까?"를 추천하죠? AI도 똑같은 원리입니다. 다만 스마트폰은 앞 단어 1~2개만 보는 반면, AI(대규모 언어모델)는 수만 단어의 맥락을 한꺼번에 보고 "다음 단어"의 확률을 계산합니다. 이걸 초당 수천 번 반복하면 그럴듯한 문장이 나옵니다.

그래서 AI는 '이해'가 아니라 '예측'이고, 가끔 그럴듯하지만 틀린 답을 지어냅니다. 이른바 '할루시네이션'입니다. 이 한계를 알면 오히려 AI를 더 잘 쓸 수 있습니다. RAG가 바로 이 문제를 보완하는 기술이고, 귀 기관의 3번 과제 방향이 정확합니다.

### 결국, 에이전트 AI의 시대

지금 AI의 최전선에서 벌어지고 있는 일은 '에이전트 AI'로의 전환입니다. 답만 뱉는 AI에서, 스스로 판단하고 도구를 쓰고 일을 끝내는 AI로. 카파시는 바이브 코딩이란 말을 만든 지 1년 만에 '에이전틱 엔지니어링'이라는 개념을 내놓았습니다. 99%의 시간 동안 직접 코드를 쓰지 않고, AI 에이전트를 지휘하며 감독하는 것이 새로운 기본값이라는 뜻입니다.

귀 기관이 시작하시는 이 여정에 정답은 없습니다. 하지만 그래서 의미가 있다고 생각합니다. 작게 시도하고, 실패하고, "어, 이게 되네?" 하는 순간을 만나고, 그게 쌓여 확신이 되는 과정. 저도 그렇게 여기까지 왔습니다.

AI 시대의 가장 큰 변화는 시행착오의 비용이 극적으로 낮아졌다는 겁니다. 한 번 실패해도 AI에게 "이거 왜 안 돼?"라고 물으면 바로 다음 시도가 가능합니다.

대면자문에도 적극 참여하여 코드 리뷰부터 개발 환경 세팅까지 실질적으로 돕겠습니다.
