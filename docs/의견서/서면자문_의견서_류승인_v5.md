# 사전기획 검토 업무 AI 전환을 위한 서면자문 의견서

**자문위원**: 류승인 | 서울특별시 광진구청 주무관 (2020~)

**작성일자**: 2026. 3. 20.

---

광진구청에서 7년째 일하는 행정직 공무원입니다. 경영학을 전공했고, 프로그래밍을 배운 적 없습니다. 다만 호기심이 좀 강한 편이라, 독학으로 코딩을 시작했고, 지난 10개월간 22개 실무 프로젝트를 직접 만들어 배포했습니다. 같은 공공기관에서 같은 고민을 먼저 해본 사람으로서, 현장 이야기를 드리려 합니다.

## 1. '내부 역량 중심 애자일 방식'에 대하여

강력히 지지합니다. 제가 걸어온 길이기도 합니다.

AI 시대에 일어난 가장 큰 변화는, 전문 개발자가 아닌 현장 사람이 직접 문제를 풀 수 있게 됐다는 것입니다. NVIDIA 젠슨 황은 "이제 모든 사람이 프로그래머"라고 했고, 하버드 컴퓨터과학 교수 출신에 구글 엔지니어링 디렉터를 지낸 Matt Welsh는 ACM에 「프로그래밍의 종말」을 기고하며, AI가 작업 설명만으로 소프트웨어를 만들어내는 시대를 예측했습니다.[1][2]

이론만이 아닙니다. 올해 2월 Anthropic의 Claude Code 해커톤에 13,000명이 지원해 227개 프로젝트가 나왔는데, 주요 수상자 5명 중 4명이 비개발자였습니다. 1등이 캘리포니아의 상해 전문 변호사, 3등이 브뤼셀의 심장내과 의사. 전문 개발자는 5명 중 1명뿐이었습니다.[3][4] 국내에서도 지난해 12월 경기도의회 바이브코딩 해커톤에서 100명이 하루 만에 60개 서비스를 배포했습니다.[5]

저 역시 경영학 전공의 행정직 공무원인데, 법령 분석 플랫폼, 문서 전문검색 앱, MCP 서버 같은 것들을 만들 수 있었습니다. 돌아보면 이유는 하나입니다. **문제를 제대로 아는 사람만이 문제를 제대로 해결할 수 있다**는 것.

용역 업체의 코딩 실력은 우리보다 뛰어납니다. 그러나 우리 업무를 모릅니다. 사전기획 검토 프로세스를 자동화한다고 해봅시다. 용역을 주면 요구사항 문서 2주, 개발 2달, 검수·수정 한 달. 그 사이에 교육부가 검토 서식을 바꾸거나 새 평가 항목을 추가하거나 관련 법령이 개정되면, 이미 만들어진 시스템을 다시 수정 요청해야 합니다. 추가 비용, 추가 기간. 반면 업무를 가장 잘 아는 담당자가 직접 만들었다면, 서식이 바뀐 그날 오후에 고칠 수 있습니다. "검토 항목 3번을 이렇게 바꿔줘"라고 AI에게 말하면 되니까요.

코딩 실력의 부족은 AI가 메워줍니다. 현장의 맥락, 업무의 깊이, "이게 왜 불편한지"를 아는 것은 AI도 용역 업체도 대체할 수 없습니다.

물론 대규모 시스템이나 보안 인프라는 전문 업체의 몫입니다. 그러나 업무 보조 도구, 데이터 전처리, 분석 자동화 같은 영역은 현장 사람이 AI와 직접 만드는 편이 낫습니다. 예산도, 속도도, 품질도.

## 2. MVP 1~3 모델의 기술적 타당성 및 고도화

먼저 밝힙니다. 저도 프로그래밍을 독학한 바이브 코더입니다. 코드를 분석할 때 제 눈만으로는 한계가 있어서, Anthropic의 최상위 모델인 Claude Opus 4.6에 심층 추론 모드(Extended Thinking)를 걸어 정밀 분석했습니다. 아래는 그 결과를 쉬운 말로 풀어 정리한 것이고, 항목마다 **AI에게 직접 수정을 요청할 수 있는 프롬프트**를 함께 드립니다. 코드를 일일이 설명드리는 것보다, 이 프롬프트를 AI에게 그대로 붙여넣는 편이 훨씬 빠르고 정확합니다.

코딩 입문 단계에서 이 정도 파이프라인을 돌아가게 만든 것 자체가 대단합니다. 방향도 맞습니다.

### MVP 1 (이미지 → AI 친화적 변환)

**잘된 점**: 여러 페이지의 병렬 처리, 실패 시 자동 재시도, 완료 페이지 건너뛰기까지 — 실무 투입에 근접한 설계입니다.

**개선 1 — dead code 정리**: `main.py`에서 1단계가 실패해 "여기서 중단"이라 적은 바로 아래에, 절대 실행될 수 없는 코드가 남아 있습니다. 검토 의견서에서 "부적합 → 반려" 결재란 아래에 "적합 시 후속 조치"가 적혀 있는 셈입니다. 반려됐으면 아래를 볼 일이 없는데 남아 있으니, 나중에 읽는 사람이 헷갈립니다. 실행에는 문제없으나 정리해 두는 게 좋겠습니다.

> 🔧 **수정 프롬프트**: "main.py를 확인해줘. except 블록 안의 return 문 아래에 도달 불가능한 dead code(주석 포함)가 있어. 실행에는 문제없지만 가독성을 위해 dead code를 정리해줘."

**문제 2 — 에러 처리가 뒤엉킴**: `ai_ocr.py`에서 에러를 4가지로 분류해 놓았는데, 마지막에 '그 외 전부'를 같이 잡아버려 앞의 분류가 무의미해졌습니다. 사업계획서 접수 양식에 "교육과정", "시설", "예산", "인력"으로 분류 체계를 만들어 놓고, 마지막에 "기타(전부)"를 두어 뭐든 기타로 빠지는 상황과 같습니다. 일시적 통신 오류는 자동 재시도하고, 코드 자체의 문제는 즉시 멈춰 알려주는 편이 원인을 훨씬 빨리 찾습니다.

> 🔧 **수정 프롬프트**: "ai_ocr.py의 예외 처리를 수정해줘. 마지막 except Exception 블록을 제거하고, API 관련 에러(RateLimitError, APIError 등)만 재시도하고 그 외 에러는 로그를 남기고 즉시 중단하도록 바꿔줘."

**문제 3 — 큰 문서에서 메모리 부족 위험**: PDF를 이미지로 변환할 때, 전체 페이지를 한꺼번에 메모리에 올립니다. 20~30페이지는 괜찮습니다. 학교별 자료를 합쳐 수백 페이지가 되면 감당이 안 됩니다. 책상 위에 서류 500장을 한꺼번에 펼치느냐, 50장씩 나눠 보느냐의 차이입니다.

> 🔧 **수정 프롬프트**: "PDF를 이미지로 변환하는 부분에서, 전체 페이지를 한 번에 변환하지 말고 first_page와 last_page 파라미터를 사용해서 20~30페이지씩 나눠서 처리하도록 수정해줘."

### MVP 2 (페이지 발췌 + 라벨링)

세 개 중 완성도가 가장 높습니다. 인터넷 없이 로컬에서 완결되고, 원본 PDF를 보호하는 안전장치도 잘 되어 있습니다.

**문제 — 프로그램 강제 종료 불가**: 에러가 나면 무조건 넘어가게 해놓은 부분이 있는데, 이러면 작업을 중단하고 싶어도 프로그램이 꺼지지 않습니다. 복사기에 종이가 걸렸는데 취소 버튼이 안 먹히는 것과 같습니다.

> 🔧 **수정 프롬프트**: "코드에서 except: 라고만 적힌 빈 예외 처리를 모두 찾아서 except Exception: 으로 바꿔줘. KeyboardInterrupt가 잡히지 않도록."

설정값(`TOPIC_FOLDERS`, `SOURCE_FILES` 등)이 코드 안에 직접 박혀 있습니다. 검토 대상 학교 목록이 프로그램 소스코드 안에 적혀 있어서, 학교가 바뀔 때마다 코드를 열어야 하는 상태입니다. 별도 설정 파일(YAML)로 분리하면 코드를 건드리지 않고 목록만 수정할 수 있습니다.

### MVP 3 (교육과정 분석)

문서를 먼저 개별 요약하고 그 결과를 모아 통합 분석하는 2단계 전략은, 대량 문서를 다루는 정석적인 접근입니다. 잘 설계되었습니다.

**문제 — 실패 알림 없음**: 1단계에서 일부 파일 요약이 실패하면 그 데이터가 2단계에서 빠지는데, 사용자에게 알림이 없습니다. 50개 학교 교육과정을 분석했는데 실제로는 8개 학교가 누락된 채 보고서가 나옵니다. 보고서만 보면 50개 전부 분석한 것처럼 보입니다. 위험합니다.

> 🔧 **수정 프롬프트**: "1단계 요약 처리에서 성공 건수와 실패 건수를 카운트하고, 2단계 통합 분석 시작 전에 '총 N개 중 M개 성공, K개 실패'를 출력하도록 수정해줘. 최종 리포트에도 이 정보를 포함시켜줘."

### 공통 개선

세 개 모두 경로, 모델명, 워커 수 같은 설정값이 코드에 박혀 있고, 실행 로그가 화면에만 나오고 파일로 남지 않습니다.

> 🔧 **수정 프롬프트**: "모든 설정값(파일 경로, 모델명, 워커 수, API키 등)을 config.yaml로 분리해줘. 그리고 logging 모듈을 사용해서 콘솔과 파일(logs/ 폴더)에 동시에 로그가 남도록 설정해줘."

위에서 지적한 사항들을 직접 개선한 구현체를 별첨으로 드립니다. 설정값 외부화(YAML), 콘솔+파일 동시 로깅, PDF 분할 처리, 성공/실패 카운트 알림뿐 아니라 — CLI 스크립트 3개를 하나의 GUI 앱으로 통합하고, 실시간 진행률 표시와 작업 취소 기능까지 넣었습니다. 코드를 건드리지 않아도 되는 설정 화면도 있어서, 비개발자가 바로 쓸 수 있는 수준을 목표로 했습니다.

## 3. 자생적 개발의 실현 가능 수준 및 예상 훈련기간

세 기능의 난이도와 학습 순서를 말씀드리겠습니다. 구체적인 기간은 적지 않겠습니다. 사람마다 배경이 다르고, 투자할 수 있는 시간이 다르고, 무엇보다 '어떤 문제를 풀고 싶은가'에 따라 속도가 완전히 달라지기 때문입니다.

**RAG 구축** (검토 의견서 DB + AI 검색)은 일종의 오픈북 시험입니다. AI가 자기 머리만 쓰는 게 아니라 준비된 문서를 펼쳐보고 답하는 방식. 진입 장벽이 가장 낮고, 도구(LangChain, LlamaIndex)도 잘 갖춰져 있어 가장 먼저 도전하기 좋습니다. "이 문서에서 관련 내용 찾아줘"가 작동하는 순간, 다음 단계로의 동기부여가 저절로 생깁니다.

**MCP 개발** (외부 데이터 연동)은 AI 세계의 USB-C입니다. 예전에 기기마다 충전기가 달랐듯, AI도 외부 시스템마다 연결 코드를 따로 짜야 했는데 이 표준 규격 덕에 한 번 만들면 어디든 꽂힙니다. 제가 국가법령정보시스템 API용 MCP 서버(64개 도구)를 만들어 오픈소스로 공개한 적 있는데, RAG를 경험한 뒤라면 자연스럽게 넘어갈 수 있습니다.

**AI 에이전트** (검토의견서 초안 자동 도출 등)는 질문에 답만 하는 게 아니라 스스로 자료를 찾고, 판단하고, 실행까지 하는 단계입니다. 가장 어렵지만, RAG와 MCP를 거치면 자연스럽게 이어집니다. 순서대로 가시면 됩니다.

### 솔직한 실패담 — 배움에는 삽질이 포함됩니다

기간보다 중요한 건, 어떤 삽질을 거치느냐입니다.

처음에는 VS Code에 GitHub Copilot을 깔고 시작했습니다. 코드를 자동완성해 준다길래 기대했는데, 문제는 그 코드가 맞는지 틀린지 판단할 능력이 저한테 없었다는 겁니다. 자동완성을 수락하고, 또 수락하고, 뭔가 점점 길어지는데 돌아가긴 하는 것 같고… 어느 순간 에러가 터지면 어디서부터 잘못된 건지 알 수가 없었습니다.

그래서 ChatGPT한테 코드를 통째로 복붙하며 "이거 고쳐줘"를 반복했습니다. 처음엔 됐습니다. 그런데 코드가 1,000줄, 2,000줄을 넘어가니까 대화창에 전체를 붙여넣을 수가 없습니다. AI가 기억할 수 있는 분량에 한계가 있으니까요. 앞부분을 잘라내면 뒷부분을 모르고, 뒷부분을 잘라내면 앞부분을 모릅니다. 2~3천 줄짜리 코드를 통째로 날려버린 적이 있습니다. 한두 번이 아닙니다.

기능을 무턱대고 추가만 한 적도 있습니다. "이것도 넣고 저것도 넣고" 하다 보니 코드가 눈덩이처럼 불어났는데, AI한테 넣으면 컨텍스트가 넘쳐서 중간을 자르고, 자른 부분에서 에러가 나고, 고치면 다른 데서 터지고. 새벽 2시에 모니터 앞에서 "아 이걸 왜 건드렸지" 하며 머리를 싸맸습니다. 한두 번이 아닙니다.

결국 대화창에서 코드를 복붙하는 방식의 한계를 깨닫고, AI가 직접 파일을 읽고 수정하고 실행하는 에이전트형 도구(Claude Code)로 넘어왔습니다. 프로젝트 전체를 이해한 상태에서 코드를 짜니까, 같은 실수가 눈에 띄게 줄었습니다.

솔직히 Claude Code도 완벽하지 않습니다. 여전히 엉뚱한 방향으로 갈 때가 있고, 예전보다 욕하는 횟수가 줄었을 뿐이지 안 하는 건 아닙니다. 다만 삽질을 거듭하면서 AI의 특성을 알게 되니까 — 어떨 때 산으로 가는지, 어떻게 지시해야 원하는 결과가 나오는지 — 헤매는 시간이 줄어드는 건 확실합니다. 도구가 완벽해서가 아닙니다. 도구를 다루는 사람이 나아진 겁니다.

귀 기관은 제 시행착오를 참고하셔서 좀 더 빠른 길로 가실 수 있을 겁니다.

## 4. AI 전환 추진 시 장애요인과 해결책

### 심리적 장벽

"프로그래밍을 배워야 하나", "프론트엔드가 뭔지도 모르는데" — 이런 생각이 첫 걸음을 막습니다. 저도 처음엔 파이썬 기초부터 배워야 하나, 데이터베이스 자격증이라도 따야 하나 진지하게 고민했습니다. 결론부터 말씀드리면, 그런 거 안 해도 됐습니다.

22개 프로젝트를 만들었지만 프로그래밍을 다 아는 건 아닙니다. 그래도 실무에서 매일 쓰는 도구들을 돌리고 있습니다. AI가 코드를 써주니까요. 바이브 코딩을 처음 정의한 안드레이 카파시(전 Tesla AI 총괄, OpenAI 공동창업자)의 말을 빌리면 — "코드가 존재한다는 사실조차 잊어라."[6]

"프로그래밍을 배운다"가 아니라 "내 업무에서 귀찮은 걸 AI한테 시켜본다"로 시작하면 됩니다.

### 현실적 장벽 — 관심은 있는데 안 배웁니다

AI 관련 동호회를 운영하면서 느낀 게 있습니다. 모임에는 꾸준히 옵니다. AI가 좋다, 배워야 한다, 입으로는 다들 동의합니다. 그런데 유료 구독까지 하는 사람은 거의 없고, 지난번에 알려드린 걸 다음 모임에서 물어보면 기억 못 하시고, 직접 해보시라고 하면 안 하십니다.

더 솔직히 말씀드리면, AI를 배우기 전에 기본적인 정보화 교육이 필요한 분들이 더 많은 게 현실입니다. 폴더 구조가 뭔지, 파일 확장자가 뭔지, 압축 파일을 어떻게 푸는지. 이런 데서 막히는 분들에게 "AI를 활용하세요"는 공허합니다.

현재 공공기관 AI 교육의 대부분은, 솔직히 프롬프트를 깎는 연습입니다. "이렇게 물어보면 더 좋은 답이 나온다" 수준. 틀린 말은 아닌데, 실무에서 체감되는 변화가 크지 않다 보니 "AI 교육 받았는데 별로 달라진 게 없다"는 인식이 퍼집니다. 진짜 변화는 AI가 내 파일을 읽고, 내 데이터를 분석하고, 내 업무를 자동화해 줄 때 비로소 시작됩니다. 현재 교육 수준으로는 거기까지 닿을 수가 없습니다.

### 구조적 장벽 — 조직의 변화는 위에서부터입니다

심리적 두려움이나 교육의 한계보다 더 근본적인 문제가 있습니다. 동기부여입니다.

바텀업으로 AI를 퍼뜨리는 데는 구조적 한계가 있습니다. AI를 열심히 배워 업무에 적용한 사람이랑 아무것도 안 한 사람 사이에 아무 차이가 없습니다. 월급이 달라지지 않습니다. 승진에 반영되지 않습니다. 오히려 잘하면 "너 좀 하네?" 소리와 함께 일만 더 늘어납니다. 이 구조에서 퇴근 후에 새로운 걸 배울 사람이 몇이나 되겠습니까.

위에서 내려오는 물결은 다릅니다. "AI 활용 실적을 인사 평가에 반영한다", "AI 역량 보유자에게 보직 우대를 준다" 같은 신호가 떨어지면, 굳이 시키지 않아도 사람들이 알아서 찾아 배우고, 자기 업무에 적용해 보지 않겠습니까. 사람은 결국 자기한테 이득이 되는 걸 배웁니다.

정부의 국가 AX(AI 대전환)도 같은 맥락입니다. 대통령실에서 방향을 잡고, 10.1조 예산을 편성하고, 전 부처에 AI 도입을 독려하는 것[7] — 현장에서 자발적으로 올라온 게 아닙니다. 위에서 길을 내야 아래가 걸어갑니다.

제 경우는 개인의 호기심과 집념으로 여기까지 왔는데, 솔직히 이건 예외에 가깝습니다. 조직 전체를 바꾸려면 열정에 기대선 안 됩니다. 열정은 소모되고, 제도는 남습니다.

제안 하나 드립니다. AI를 쓰는 직원이 실질적으로 인정받는 구조를 먼저 만들어 보십시오. 인사 가점이든, 전문직위 지정이든, 성과급이든 형태는 상관없습니다. "AI를 쓰면 나한테 좋은 일이 생긴다"는 신호만 분명하면, 교육 프로그램을 짜기도 전에 사람들이 움직이기 시작할 겁니다.

## 5. 최적의 '바이브 코딩 툴' 추천

하나만 쓰라면 Claude Code입니다. 다만 솔직히 저는 세 가지를 다 씁니다. ChatGPT(GPT), Claude, Gemini — 각각 잘하는 게 다르고, 서로 보완재이기 때문입니다.

### 코딩 도구로서의 비교

주요 바이브 코딩 도구들(Cursor, GitHub Copilot, Windsurf)은 코드 편집기 안에서 AI가 보조하는 방식입니다. Claude Code는 다릅니다. AI가 직접 파일을 읽고, 코드를 고치고, 실행하고, 테스트까지 합니다. 입문자한테는 편집기를 익히는 것부터가 허들인데, Claude Code는 말로 지시하면 됩니다. 이를테면:

- "이 폴더에 있는 PDF 50개에서 텍스트를 뽑아서 엑셀로 정리해줘"
- "이 엑셀 파일에서 중복된 행을 찾아서 표시해줘"
- "이 파이썬 코드가 에러가 나는데 원인 찾아서 고쳐줘"
- "이 웹사이트에서 매일 공지사항을 긁어오는 프로그램 만들어줘"

한국어로 말하면 AI가 알아서 코드를 짜고, 실행하고, 안 되면 스스로 수정합니다.

코딩 역량만 놓고 보면, 현재 기준 제 체감은 Claude > GPT Codex >>>> Gemini 순입니다. Claude와 Codex는 서로 부족한 부분을 정확히 메워주는 보완재입니다. Claude가 막힐 때 Codex한테 넘기면 돌파구가 열리고, 반대도 마찬가지입니다. 22개 프로젝트를 주로 Claude Code로 만들었는데, Rust 데스크톱 앱부터 Next.js 웹 플랫폼, MCP 서버까지 하나의 도구로 다 다뤘습니다.

### Gemini의 강점 — API 활용

Gemini는 코딩 도구로서는 위 둘에 못 미칩니다. 그러나 API 활용에서는 확실한 강점이 있습니다. 무료 사용량이 넉넉하고, 유료 전환해도 토큰당 비용이 저렴합니다. 100만 토큰이 넘는 컨텍스트 윈도우, 이미지·영상·음성을 한 번에 처리하는 멀티모달 기능까지 갖추고 있어서, 이미 짜여진 코드 안에 AI 기능을 붙여야 할 때 — 문서 요약, 이미지 텍스트 추출, 대량 데이터 분류 같은 용도에서 — 가성비가 가장 좋습니다. 귀 기관의 MVP에서 OCR이나 문서 분석에 Gemini API를 쓰고 계신 것도 같은 이유일 겁니다.

Claude는 API 비용이 부담스러운 게 사실입니다. 그래서 코딩은 Claude Code 구독으로, AI 서비스 기능은 Gemini API로 나눠 쓰는 게 현실적인 조합입니다.

물론 자고 일어나면 판이 바뀌는 게 AI 세계입니다. 이 비교는 2026년 3월 기준이고, 몇 달 후면 달라져 있을 수 있습니다.

### 윈도우 환경

윈도우도 됩니다. 저도 전부 윈도우에서 했습니다. Git Bash나 WSL을 쓰면 문제없고, 초기 세팅도 AI가 도와줍니다. 공공기관이 윈도우를 쓴다면 윈도우에서 개발하는 게 오히려 자연스럽습니다.

### 인프라 규모

Claude Code 구독이 월 $20~200(사용량에 따라 다름), Gemini API 크레딧은 기존 계획대로 300 USD면 MVP 개발·테스트에 충분합니다. 저는 개인적으로 GPT 팀플랜, Gemini 연간 구독(할인 시기에 50%로 구매), Claude Max 플랜을 병행하고 있는데, 기관 규모와 예산에 맞게 조합하시면 됩니다. Anthropic이 올해 초 서울에 한국 사무소를 열 예정이라 공공기관 지원이 확대될 수 있습니다.[8]

## 6. 정보 보안 및 LLM 윤리

보안은 반드시 지켜야 합니다. 동시에, 막연한 두려움이 혁신의 문을 닫아서도 안 됩니다.

### 기준이 되는 가이드라인

국정원이 2025년 12월에 배포한 「AI 보안 가이드북」이 기준입니다. 15개 위협 유형에 30개 대책을 매칭해 놓았고, 핵심은 셋입니다 — 신뢰할 수 있는 데이터만 쓸 것, 개인정보 사전 검사, 접근 통제와 로깅.[9]

19년간 유지된 획일적 망분리도 변하고 있습니다. 업무 중요도에 따른 3등급(기밀·민감·공개) 차등 보안 — 국가망보안체계(N²SF) 전환입니다.[10] 공공기관도 AI와 클라우드를 쓸 수 있는 길이 열렸습니다.

해외 모델의 보안이 걱정되신다면, 국내 AI 모델도 빠르게 공공 영역에 진입하고 있습니다. 정부의 '범정부 초거대AI 공통기반 구축 사업'에 삼성SDS·LG CNS·KT 컨소시엄이 참여하여, 공무원이 보안 걱정 없이 생성형 AI를 쓸 수 있는 인프라를 만들고 있고[17], 네이버 하이퍼클로바X는 이미 부산시 전 부서 약 6,000명 대상으로 행정 서비스에 투입되었으며[18], LG AI연구원의 엑사원(EXAONE)은 기업·공공기관용 AI 에이전트 '챗엑사원' 베타 서비스를 시작했습니다.[19] 국내 데이터센터에서 돌아가는 국산 모델이니 해외 서버로 데이터가 나가는 부담이 줄고, 보안 장벽이 한층 낮아지는 흐름입니다.

### 실무에서 이렇게 하면 됩니다

가이드라인이 있어도 "그래서 실무에선 어떻게?" — 제가 실제로 지키고 있는 원칙을 공유드립니다.

**1단계 — 데이터 분류 먼저.** AI에 넣기 전에 "이 데이터가 공개해도 되는 건가?"를 판단합니다. 법령, 지침, 서식, 교육과정 같은 건 대부분 이미 공개된 행정 데이터입니다. 정보공개율이 최근 5년간 약 94%를 유지하고 있습니다.[11] 반면 민원인 이름, 주민번호, 내부 인사 자료는 절대 넣지 않습니다.

**2단계 — 개인정보 마스킹.** 혹시라도 개인정보가 섞여 있을 수 있으니, AI에 넣기 전에 이름은 "○○○", 전화번호는 "010-\*\*\*\*-\*\*\*\*"로 바꿉니다. 개인정보보호위원회의 「생성형 AI 개인정보 처리 안내서」(2025. 8.)가 기준이고[12], 이미지·영상 같은 비정형 데이터 가명처리 기준도 2024년에 마련되어 있습니다.[13]

**3단계 — API 우선, 웹 대화창 지양.** 웹 브라우저의 ChatGPT/Claude 대화창은 입력 내용이 학습 데이터로 쓰일 가능성이 있습니다(설정에 따라 다르지만). API를 통해 호출하면 기본적으로 학습에 사용되지 않는다는 정책이 대부분의 LLM 사업자에게 적용됩니다. 가능하면 API 기반으로 쓰는 게 안전합니다.

**4단계 — 결과물 검증 습관화.** AI가 생성한 내용은 반드시 사람이 검토합니다. 특히 수치, 법령 인용, 고유명사는 AI가 그럴듯하게 지어내는 경우가 있으므로 원문 대조를 습관화해야 합니다.

**5단계 — 로그 남기기.** 어떤 데이터를 어떤 AI에 넣었는지, 어떤 결과가 나왔는지를 간단히라도 기록해 두면 감사나 보안 점검 시 대응이 가능합니다.

서울시가 29개 생성형 AI 모델을 업무에 개방했고(서울AI챗)[14], 전국 공공기관들이 속속 AI 도입 계약을 맺고 있는 흐름입니다. 가이드라인을 지키면 충분히 활용할 수 있습니다.

## 7. 추가 제언

### 대화창 AI와 바이브 코딩은 다릅니다

많은 분들이 ChatGPT나 Claude 웹에서 질문하고 답 받는 것을 'AI 활용'이라 여기십니다. 맞긴 합니다. 그러나 거기엔 분명한 한계가 있습니다.

엑셀 파일 100개에서 특정 데이터를 뽑아 하나로 합쳐야 한다고 해봅시다. 대화창 AI한테 물어보면 "Python으로 이렇게 하세요"라며 코드를 알려줍니다. 그럼 그 코드를 복사해서, 파이썬을 설치하고, 파일을 옮기고, 터미널을 열고, 실행해 보고, 에러가 나면 다시 대화창에 붙여넣고… 이 과정을 전부 사람이 해야 합니다.

바이브 코딩은 다릅니다. "이 폴더에 있는 엑셀 100개에서 '예산집행액' 열만 뽑아서 하나로 합쳐줘"라고 말하면 끝입니다. AI가 직접 폴더를 열고, 파일을 읽고, 코드를 짜고, 실행하고, 에러가 나면 스스로 고치고, 결과 파일을 만들어 줍니다. 사람은 결과만 확인하면 됩니다.

대화창에서 "답변을 받는" 시대에서, AI가 "일을 해주는" 시대로 넘어가고 있습니다.

### AI가 말을 잘한다고 맞는 말을 하는 건 아닙니다

AI가 어떻게 작동하는지 아주 쉽게 설명드리겠습니다. 카카오톡에서 "오늘 점심" 치면 "뭐 먹을까?" 뜨죠? AI도 같은 원리입니다. 앞 단어 1~2개가 아니라, 수만 단어의 맥락을 한꺼번에 보고 다음 단어의 확률을 계산한다는 점이 다를 뿐.

여기서 핵심 기술이 2017년에 나온 '트랜스포머(Transformer)'입니다. 원리는 이렇습니다. 시험 문제를 풀 때 문제를 읽으면서 "이 부분이 중요하겠다"고 밑줄을 긋잖아요? 트랜스포머도 마찬가지입니다. 문장의 모든 단어가 다른 모든 단어를 바라보면서, 지금 이 맥락에서 어디에 주목해야 하는지를 스스로 계산합니다. 이걸 '어텐션(Attention)'이라 합니다. 이 덕분에 AI가 긴 문장도 맥락을 놓치지 않고 자연스럽게 이어 쓸 수 있게 됐습니다.

문제는 여기서부터입니다. 이 방식은 **문법적으로 완벽한 문장을 만드는 데는 탁월하지만, 내용이 사실인지는 전혀 별개의 문제**라는 것. AI는 "다음에 올 가능성이 가장 높은 단어"를 예측할 뿐이지, 그게 맞는 말인지 검증하는 장치가 없습니다.

그래서 AI는 아주 자신감 넘치는 말투로 완전히 틀린 얘기를 합니다. 존재하지 않는 논문을 인용하고, 없는 법 조항을 만들어내고, 그럴듯한 통계를 지어냅니다. 이른바 할루시네이션. 공냥이(@specal1849) 강사를 비롯해 많은 AI 교육 전문가들이 공통적으로 강조하는 지점이기도 합니다 — AI의 출력은 "유창함"이지 "정확함"이 아니라는 것.[16]

이 한계를 알면 오히려 AI를 더 잘 쓸 수 있습니다. RAG가 바로 이 문제를 잡는 기술입니다 — AI한테 "네 머리로 답하지 말고 이 문서에서 찾아서 답해"라고 시키는 것이니까요. 귀 기관의 3번 과제 방향이 정확합니다.

### 에이전트 AI의 시대

기존 AI와 에이전트 AI의 차이를 하나만 들겠습니다.

**기존 AI**는 식당의 키오스크입니다. 내가 메뉴를 고르고, 버튼을 누르고, 결제하고, 음식을 받아옵니다. AI는 주문을 처리해 줄 뿐, 나머지는 전부 내 몫입니다.

**에이전트 AI**는 일 잘하는 신입 직원에 가깝습니다. "이번에 들어온 사업계획서, 작년에 비슷한 거 있었는지 찾아보고, 있으면 그때 검토 의견이랑 비교해서 이번 건의 쟁점을 정리해줘"라고 하면 — 스스로 파일을 뒤지고, 관련 문서를 찾고, 비교 분석해서 정리된 결과를 가져옵니다. 중간에 "이 부분은 판단이 안 서는데 어떻게 할까요?"라고 물어오기도 합니다.

키오스크는 버튼을 하나하나 눌러야 합니다. 신입 직원한테는 "이거 해줘" 한마디면 됩니다. 지금 AI가 키오스크에서 신입 직원으로 바뀌고 있습니다.

카파시는 바이브 코딩이란 말을 만든 지 정확히 1년 뒤인 올해 2월, 이 변화를 '에이전틱 엔지니어링'이라 이름 붙였습니다.[15] 사람이 직접 하나하나 하는 게 아니라 AI 에이전트한테 일을 맡기고 감독하는 것이 새로운 기본값이 된다는 뜻입니다.

귀 기관의 업무로 옮기면 이런 겁니다. 새 사업계획서가 접수되면, 에이전트가 과거 검토 의견서 DB에서 유사 사례를 찾고, 이전에 지적된 쟁점을 자동으로 뽑아내고, "이번 건에서도 같은 문제가 있을 수 있다"는 초안 리포트를 만들어 놓습니다. 담당자는 그 초안을 검토하고 판단만 하면 됩니다. 지금 바로 되는 건 아니지만, RAG → MCP → 에이전트 순서로 역량을 쌓으시면 도달할 수 있는 단계입니다.

Anthropic의 CEO 다리오 아모데이는 2025년 에세이에서, AI가 1~2년 내에 대부분의 지식 업무에서 "매우 유능한 주니어 직원" 수준에 도달할 것으로 전망했습니다. 그러면 사람이 할 일이 없어지느냐. 오히려 반대입니다. AI가 자료 조사, 초안 작성, 데이터 정리 같은 반복 업무를 맡아주면, 사람은 판단과 기획에 집중할 수 있게 됩니다. 혼자서 처리할 수 있는 업무량이 몇 배로 늘어납니다. AI를 잘 다루는 사람이 더 많은 일을 해내는 시대가 오고 있습니다.

이 흐름에 올라타느냐 마느냐의 차이가, 앞으로 몇 년 안에 꽤 크게 벌어질 수 있습니다.
