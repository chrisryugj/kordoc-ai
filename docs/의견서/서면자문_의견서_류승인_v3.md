# 사전기획 검토 업무 AI 전환을 위한 서면자문 의견서

**자문위원**: 류승인 | 서울특별시 광진구청 주무관 (2020~)

**작성일자**: 2026. 3. 20.

---

광진구청에서 6년째 일하고 있는 행정직 공무원입니다. 전산학을 전공한 적 없습니다. 그런데 틈틈이 코딩을 독학해서, 지난 10개월간 22개 실무 프로젝트를 직접 만들고 배포했습니다. 같은 공공기관에서 같은 고민을 먼저 해본 사람으로서, 현장 이야기를 좀 드리겠습니다.

## 1. '내부 역량 중심 애자일 방식'에 대하여

내부 역량 중심 애자일 방식, 강력히 지지합니다. 제가 걸어온 길이기도 합니다.

AI 시대의 가장 큰 변화가 뭐냐면, 전문 개발자가 아니라 현장 사람이 직접 문제를 풀 수 있게 됐다는 겁니다. NVIDIA 젠슨 황이 "이제 모든 사람이 프로그래머"라고 했고, 하버드 컴퓨터과학 교수 출신에 구글 엔지니어링 디렉터를 지낸 Matt Welsh는 ACM에 「프로그래밍의 종말」이란 글을 기고하면서, AI가 작업 설명만으로 소프트웨어를 만들어내는 시대를 예측했습니다.[1][2]

이론만은 아닙니다. 올해 2월 Anthropic이 연 Claude Code 해커톤에 13,000명이 지원하고 227개 프로젝트가 나왔는데, 주요 수상자 5명 중 4명이 비개발자였습니다. 1등이 캘리포니아의 상해 전문 변호사, 3등이 브뤼셀의 심장내과 의사. 전문 개발자는 5명 중 1명뿐이었습니다.[3][4] 국내에서도 지난해 12월 경기도의회에서 열린 바이브코딩 해커톤에서, 100명이 하루 만에 60개 서비스를 배포한 사례가 있습니다.[5]

저도 비슷합니다. 행정학 전공인 제가 법령 분석 플랫폼, 문서 전문검색 앱, MCP 서버 같은 걸 만들 수 있었던 건, 현장에서 매일 부딪히는 문제를 잘 알았기 때문입니다.

용역 업체는 우리 업무를 모릅니다. 요구사항 전달하고, 개발하고, 검수하고, 수정 요청하고… 그 사이에 현장은 벌써 바뀌어 있습니다. 담당자가 직접 만들면 아침 아이디어를 점심에 프로토타입으로 돌려볼 수 있습니다.

대규모 시스템이나 보안 인프라는 당연히 전문 업체가 해야죠. 하지만 업무 보조 도구, 데이터 전처리, 분석 자동화 같은 영역은 현장 사람이 AI와 직접 만드는 게 낫습니다. 예산도, 속도도, 품질도.

## 2. MVP 1~3 모델의 기술적 타당성 및 고도화

코딩 입문 단계에서 이 정도 파이프라인을 돌아가게 만든 것 자체가 대단합니다. 방향도 맞습니다. 코드를 살펴보니 몇 군데만 잡으면 훨씬 단단해질 수 있어서 짚어 드립니다.

### MVP 1 (이미지 → AI 친화적 변환)

**잘된 점**: 병렬 처리(ThreadPoolExecutor), 지수 백오프 재시도, 처리 완료 페이지 건너뛰기까지 — 프로덕션에 근접한 설계입니다.

**고칠 점**:

`main.py`에 2단계(OCR)가 아예 실행이 안 되는 버그가 있습니다. `return` 문 뒤에 `time.sleep(2)`가 위치해서 1단계 끝나면 그냥 빠져나옵니다. 들여쓰기 한 단계만 빼면 고쳐지는데, 이게 프로그램 전체 흐름을 막고 있어서 가장 먼저 잡아야 합니다.

`ai_ocr.py` 예외 처리에서 API 오류 4종을 구분해 놓고 마지막에 `Exception`을 같이 잡아서, 앞의 4개가 무의미해졌습니다. API 일시 오류만 재시도하고 나머지는 즉시 멈추게 하세요.

PDF → 이미지 변환 시 전체 페이지를 한꺼번에 메모리에 올립니다. 수백 페이지짜리를 돌리면 터질 수 있으니 `first_page`/`last_page`로 20~30장씩 끊으세요.

### MVP 2 (페이지 발췌 + 라벨링)

세 개 중 완성도가 가장 높습니다. 외부 API 없이 오프라인 완결이고, PdfReader 캐싱이나 `copy.copy` 원본 보호 같은 부분도 잘 되어 있습니다.

`except:`(빈 예외 처리)가 몇 군데 있어서 Ctrl+C가 먹히지 않습니다. `except Exception:`으로 바꾸세요. `TOPIC_FOLDERS` 같은 설정값은 YAML로 빼면 재사용이 편해집니다.

### MVP 3 (교육과정 분석)

2단계 요약(개별 → 통합)은 대량 문서 분석의 정석입니다. 'Architect-Collaborator' 페르소나 프롬프트 설계도 좋습니다.

하나. 1단계에서 일부 파일이 실패하면 그 데이터가 2단계에서 빠지는데, "10개 중 7개만 됐다"는 안내가 없습니다. 불완전한 결과를 완전한 것으로 착각할 수 있으니 성공/실패 카운트를 리포트에 넣으세요.

### 공통

세 개 다 경로, 모델명, 워커 수가 코드에 박혀 있습니다. YAML 하나로 빼면 다른 PC에서 돌릴 때 코드를 안 건드려도 됩니다. 콘솔 로그만 있는 것도 파일 로그를 추가하면 이력 추적에 쓸 수 있습니다.

개선을 반영한 구현체를 별첨으로 드립니다.

## 3. 자생적 개발의 실현 가능 수준 및 예상 훈련기간

**RAG 구축** (검토 의견서 DB + AI 검색): '오픈북 시험'이라 보면 됩니다. AI가 자기 머리만 쓰는 게 아니라 준비된 문서를 찾아보고 답하는 방식. 진입 장벽이 가장 낮고 도구(LangChain, LlamaIndex)도 잘 갖춰져 있어서, 본업 하면서 2~4개월이면 기본 시스템을 세울 수 있습니다. 환각 방지는 "어느 문서 몇 페이지에서 가져왔다"를 같이 보여주는 게 가장 확실합니다.

**MCP 개발** (외부 데이터 연동): 'AI 세계의 USB-C'입니다. 기기마다 충전 단자가 달랐던 것처럼 AI도 외부 시스템마다 연결 코드를 따로 짜야 했는데, 이 표준 규격 덕에 한 번 만들면 어디든 꽂힙니다. 제가 국가법령정보시스템 API용 MCP 서버(64개 도구)를 만들어 오픈소스로 공개한 적 있는데, 3~6개월 잡으면 됩니다.

**AI 에이전트** (검토의견서 초안 자동 도출 등): 질문에 답만 하는 게 아니라 스스로 자료를 찾고, 판단하고, 실행까지 하는 단계입니다. 가장 어렵고 6개월~1년은 봐야 합니다. RAG, MCP를 거치면 자연스럽게 이어지니 순서대로 가시면 됩니다.

## 4. AI 전환 추진 시 장애요인과 해결책

### 심리적 장벽

"프로그래밍을 배워야 하는 거 아닌가…" "프론트엔드가 뭔지도 모르는데…" 이런 생각이 첫 걸음을 막습니다.

저도 22개 프로젝트를 만들었지만 프로그래밍을 다 아는 건 아닙니다. 그래도 법령 분석 플랫폼이랑 소식지 생성 시스템을 매일 실무에서 씁니다. AI가 코드를 써주니까요. 바이브 코딩을 처음 정의한 안드레이 카파시(전 Tesla AI 총괄, OpenAI 공동창업자)가 이렇게 말했습니다 — "코드가 존재한다는 사실조차 잊어라."[6]

"프로그래밍을 배운다"고 시작하지 마세요. "내 업무에서 귀찮은 걸 AI한테 시켜본다"로 시작하면 됩니다.

### 구조적 장벽 — 조직의 변화는 위에서부터입니다

심리적 두려움보다 더 근본적인 문제가 있습니다.

바텀업으로 AI를 퍼뜨리는 건 구조적으로 한계가 있습니다. AI를 열심히 배워 업무에 적용한 사람이랑 아무것도 안 한 사람 사이에 아무 차이가 없거든요. 월급이 달라지지 않습니다. 승진에 반영되지 않습니다. 오히려 잘하면 "너 좀 하네?" 소리와 함께 일만 더 늘어납니다. 이 구조에서 퇴근 후에 새로운 걸 배울 사람이 몇이나 되겠습니까.

위에서 내려오는 물결은 다릅니다. "AI 활용 실적을 인사 평가에 반영한다." "AI 역량 보유자에게 보직 우대를 준다." 이런 신호가 떨어지면 시키지 않아도 사람들이 알아서 찾아 배우고, 자기 업무에 적용하고, 옆 사람한테 물어봅니다.

정부의 국가 AX(AI 대전환)도 같은 논리입니다. 대통령실에서 방향을 잡고, 10.1조 예산을 편성하고, 전 부처에 AI 도입을 독려하는 건[7] — 현장에서 자발적으로 올라온 게 아닙니다. 위에서 길을 내야 아래가 걸어갑니다.

제 경우는 개인의 호기심으로 여기까지 왔는데, 솔직히 이건 예외입니다. 조직 전체를 바꾸려면 열정에 기대선 안 됩니다. 열정은 소모되고 제도는 남으니까요.

제안드립니다. AI를 쓰는 직원이 실질적으로 인정받는 구조를 먼저 만드세요. 인사 가점이든, 전문직위 지정이든, 성과급이든 형태는 상관없습니다. "AI를 쓰면 나한테 좋은 일이 생긴다"는 신호만 분명하면, 교육 프로그램을 짜기도 전에 사람들이 움직이기 시작합니다.

## 5. 최적의 '바이브 코딩 툴' 추천

Claude Code를 추천합니다.

주요 바이브 코딩 도구들(Cursor, GitHub Copilot, Windsurf)은 코드 편집기 안에서 AI가 보조하는 방식입니다. Claude Code는 AI가 직접 파일을 읽고, 코드를 고치고, 실행하고, 테스트까지 합니다. 입문자한테는 편집기를 익히는 것부터가 허들인데, Claude Code는 말로 지시하면 됩니다. 이 차이가 큽니다.

22개 프로젝트를 전부 이걸로 만들었습니다. Rust 데스크톱 앱, Next.js 웹 플랫폼, MCP 서버까지 하나의 도구로.

윈도우도 됩니다. 저도 전부 윈도우에서 했습니다. Git Bash나 WSL을 쓰면 문제없고, 초기 세팅도 AI가 도와줍니다. 공공기관이 윈도우를 쓴다면 윈도우에서 개발하는 게 오히려 맞습니다.

**인프라**: Claude Code 구독 월 $20~100(사용량 따라), Gemini API 크레딧 300 USD면 MVP 개발·테스트에 충분합니다. Anthropic이 올해 초 서울에 한국 사무소를 열 예정이라 공공기관 지원이 늘어날 수 있습니다.[8]

## 6. 정보 보안 및 LLM 윤리

보안은 지켜야 합니다. 동시에 막연한 두려움이 혁신을 가로막아서도 안 됩니다.

기준은 국정원이 2025년 12월에 배포한 「AI 보안 가이드북」입니다. 15개 위협 유형에 30개 대책을 매칭해 놓았고, 핵심은 셋 — 신뢰할 수 있는 데이터만 쓸 것, 개인정보 사전 검사, 접근 통제와 로깅.[9]

더 큰 변화가 있습니다. 19년간 유지된 획일적 망분리가 업무 중요도에 따른 3등급(기밀·민감·공개) 차등 보안으로 바뀌었습니다. 국가망보안체계(N²SF) 전환입니다.[10] 공공기관도 AI와 클라우드를 쓸 수 있는 길이 열린 겁니다.

현장 경험으로 말씀드리면, 공직 6년간 진짜 비공개해야 할 문서는 손에 꼽았습니다. 개인정보가 든 민원 서류, 감사 관련 내부 문서 정도. 사전기획팀이 다루시는 법령, 지침, 서식, 교육과정은 대부분 이미 공개된 행정 데이터입니다. 실제로 정보공개율이 최근 5년간 약 94%를 유지하고 있습니다.[11]

AI에 데이터를 넣기 전 개인정보만 마스킹하면 됩니다. 개인정보보호위원회의 「생성형 AI 개인정보 처리 안내서」(2025. 8.)가 기준이고[12], 이미지·영상·텍스트 같은 비정형 데이터에 대한 가명처리 기준도 2024년 2월에 나왔습니다.[13]

서울시가 29개 생성형 AI 모델을 업무에 개방한 것(서울AI챗)[14], 전국 공공기관들이 속속 AI 도입 계약을 맺고 있는 것 — 보안 가이드라인을 지키면서 적극 활용하시길 권합니다.

## 7. 추가 제언

### 대화창 AI와 바이브 코딩은 다릅니다

ChatGPT나 Claude 웹에서 질문하고 답 받는 것도 AI 활용이긴 한데, 한계가 분명합니다. 대화창의 AI는 우리 컴퓨터 파일을 못 읽고, 코드를 못 돌리고, 결과도 못 봅니다. 복붙은 전부 사람 몫입니다.

바이브 코딩은 다릅니다. AI가 직접 파일을 읽고 코드를 쓰고 실행하고 오류까지 고칩니다. 사람은 방향만 잡아주면 됩니다. 이게 '에이전트 AI'이고, 지금 전 세계가 여기로 달리고 있습니다.

### AI는 확률 계산기입니다

카카오톡에서 "오늘 점심" 치면 "뭐 먹을까?" 뜨죠? AI도 같은 원리입니다. 다만 앞 단어 1~2개가 아니라 수만 단어의 맥락을 보고 다음 단어의 확률을 계산합니다. 초당 수천 번 반복하면 그럴듯한 문장이 나옵니다.

그래서 AI는 '이해'가 아니라 '예측'입니다. 가끔 그럴듯하지만 틀린 답을 지어내는데 이걸 할루시네이션이라 합니다. RAG가 이 문제를 잡는 기술이고, 귀 기관의 3번 과제 방향이 맞습니다.

### 에이전트 AI의 시대

카파시는 바이브 코딩이란 말을 만든 지 정확히 1년 뒤인 올해 2월, '에이전틱 엔지니어링'이란 개념을 내놨습니다.[15] 99%의 시간 동안 직접 코드를 쓰지 않고, AI 에이전트를 지휘하고 감독하는 것이 새로운 기본값이라는 뜻입니다. 답만 뱉는 AI에서, 스스로 판단하고 도구를 쓰고 일을 끝내는 AI로.
