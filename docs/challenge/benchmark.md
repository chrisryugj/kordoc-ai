# 한글 공문서 작성 도구 비교 측정

2026-10-10 측정. 측정 하네스(`bench/compare`)의 실행 코드·입력·원본 숫자(results.json)는 비교 도구의 실명·저장소 주소와 측정 PC 의 경로가 들어 있어 공개 저장소에 올리지 않음. 아래에 나오는 `bench/compare/…` 경로는 그 비공개 하네스를 가리키고, 무엇을 어떻게 쟀는지는 [bench/compare/README.md](../../bench/compare/README.md)에 있음.
비교 도구는 익명(도구 A~G)으로 적음. 숫자는 이번 측정값만 씀.

## 1. 비교 대상과 과제

조사 7종, 실제로 돌린 것 3종(도구 A·C 생성, 도구 B 검사 모듈), 나머지는 공개 설명서로 기능 표만. 판독기로 hwpxlib(자바)·도구 D·rhwp·kordoc 을 씀.

| 표기 | 성격 | 이번에 |
| --- | --- | --- |
| 도구 A | 보고서·보도자료 HWPX 생성 MCP 서버(파이썬, 52개 중앙부처 서식 실측값) | 실행 |
| 도구 B | 다 쓴 한글 보고서 후처리 프로그램(자간·서식 통일·한 번에 적용) | 본 기능은 Windows + 한/글 자동화라 못 돌림. 검사 모듈만 실행, 본래 과제는 그 도구가 공개한 실행 결과로 비교 |
| 도구 C | AI 에이전트용 HWP·HWPX 스킬(파이썬, 원샷 명세 생성·양식 채우기·HWP 변환) | 실행 |
| 도구 D | HWPX 읽기·편집·생성 파이썬 라이브러리 | 판독기로만(생성은 코드 작성 필요, 도구 C 의 바탕) |

## 2. 핵심 과제: 메모 → 개조식 보고서 HWPX

입력: `bench/compare/inputs/` 의 메모 3건(짧은 메모·숫자와 표가 든 메모·회의 메모, 가상의 가온시).

### 2-1. 전체 과정 (같은 메모, 같은 로컬 AI)

- AI: 양쪽 모두 이 PC 의 Ollama `gemma4:e4b`, 요청 모양(스트리밍·사고 끔·최대 길이)도 같게. 유료 API 호출 없음.
- 지시문: "다음 메모를 개조식 보고서로 만들어 주세요." + 메모 원문.
- kordoc-ai: 앱 엔진 그대로(AI 초안 → 보고서 프리셋 생성), 폐쇄망 모드 켬. 초안이 표기법 오류면 한 번 고쳐 씀(앱 동작).
- 도구 A: 그 도구가 내는 작성 규칙을 AI 에 주고 구조 JSON 을 받아 생성. 도구 안내대로 고칠 점이 나오면 한 번 다시 받음.
- 사람 판정: 메모마다 핵심 사실 점검표(11·16·13항목)로 결과를 읽고 맞음·틀림·빠짐, 메모와 어긋나거나 지어낸 서술을 셈(`fact-audit.json`).

| 항목 | kordoc-ai | 도구 A |
| --- | --- | --- |
| 핵심 사실 맞음 | 107/120 (89.2%) | 91/120 (75.8%) |
| 틀림 · 빠짐 | 2 · 11 | 4 · 25 |
| 어긋나거나 지어낸 서술 (9문서) | 12건 | 11건 |
| 메모 숫자 보존율(자동) | 평균 95.8% | 평균 88.9% |
| 문서 1건 시간(AI 포함) | 평균 18.9초 (13.7~22.6) | 평균 53.4초 (33.4~92.7) |
| AI 호출 두 번째(고쳐 받기) | 앱 안에서 처리 | 9회 중 3회 |
| 표가 들어간 문서 | 0/9 | 9/9 (문서당 평균 1.8개) |
| 요약 상자 · 장 제목 · 쪽번호 | 9/9 · 9/9 · 9/9 | 0/9 · 8/9 · 0/9 |
| 외부 인터넷 요청 | 0건(앱 보안 기록) | 도구 자체 통신 없음(코드 확인) |

틀림의 예: 양쪽 모두 "추가 2대 + 교체 1대"를 "총 3대 운영"으로 씀(운영은 4대). 도구 A 는 "31건 → 18건"을 증가로, 작성일을 작성 규칙 예시의 날짜(2026. 10. 7.)로 넣은 문서가 있었음. 도구 A 예비 실행 1회에서는 AI 가 행 없는 표 블록을 보내 생성 중 멈춤(점검기는 경고만 내고 생성은 진행).

### 2-2. 조판만 (같은 개요)

메모를 사람이 정리한 같은 개요(제목·요약 한 문장·장·□ㅇ- 항목·표)를 각 도구의 정식 입력 꼴로만 옮겨 넣음. 요약 상자가 없는 형식은 그 도구 안내대로 첫 □ 문장이나 리드 문단으로 넣음.

| 서식 요소 (3건 중) | kordoc-ai 보고서 | kordoc-ai 개조식 | 도구 A | 도구 C 기본계획형 | 도구 C 요약보고형 |
| --- | --- | --- | --- | --- | --- |
| 제목 상자·띠 | 3 | 3 | 3 | 3 | 3 |
| 요약 상자 | 3 | 3 | 0 | 3 | 0 |
| 장 제목(Ⅰ Ⅱ) | 3 | 3 | 3 | 3 | 0 |
| 항목 위계 들여쓰기 | 3 | 3 | 3 | 3 | 3 |
| 단계별 서식 일관 | 3 | 3 | 3 | 3 | 3 |
| □·ㅇ 서식 구분 | 3 | 3 | 0 | 0 | 3 |
| 표 머리 음영 | 3 | 3 | 3 | 3 | 3 |
| 쪽번호 | 3 | 3 | 0 | 0 | 0 |
| 개요 글 누락 | 0 | 0 | 0 | 0 | 0 |
| 평균 쪽 수 | 1.7 | 3.7(표지·목차) | 1.7 | 1.0 | 1.0 |
| 1건 생성(프로세스 시작 포함) | 137ms | 128ms | 320ms | 106ms | 104ms |

□·ㅇ 서식 구분과 쪽번호는 각 도구의 기본 서식 선택이라 좋고 나쁨이 아니라 차이로 봄. 생성 시간은 모두 1초 안이라 실무 차이 없음.

### 2-3. 다른 엔진에서 열리나

| 판독기 | kordoc-ai 마크다운 생성 20건 | 도구 A 12건 | 도구 C 생성 8건 |
| --- | --- | --- | --- |
| rhwp 전 쪽 그리기 | 20/20 | 12/12 | 8/8 |
| kordoc 읽기·구조 검증 | 20/20 | 12/12 | 8/8 |
| 도구 D | 20/20 | 12/12 | 8/8 |
| 도구 B·도구 C 검증기 | 20/20 | 12/12 | 8/8 |
| hwpxlib(자바) | 0/20 | 12/12 | 8/8 |

hwpxlib 는 `version.xml` 이 없으면 "not hwpx file" 로 거부함. kordoc 생성 패키지에는 `version.xml`·`settings.xml`·`META-INF/manifest.xml` 이 없음(한컴 저장본과 도구 A·C 생성본에는 있음). kordoc-ai 의 내장 기안문 서식 채움(1/1)과 HWP 변환(9/10)은 열림.

### 2-4. 표기 규정 (검사기 4종을 모든 결과에)

kordoc 표기법·개조식 문체, 도구 A 점검기, 도구 B 검토기, 도구 C 표기 검수기를 모든 결과에 똑같이 돌림. 보고서 결과물 전체에서 실제 표기 위반은 세 도구 모두 0건. 걸린 것은 검사기 쪽 오독이었음:

- 도구 B·C 검사기는 날짜 안 묶음 빈칸(줄 끝에서 날짜가 갈리지 않게 하는 빈칸)을 글로 안 읽어 "2026.8.12."로 보고 빈칸 누락이라 함(kordoc-ai·도구 A 둘 다 해당).
- 도구 B 검토기는 kordoc 의 "부호 + 탭"을 부호로 못 알아봐 서식 편차를 냄(원본 7건 → 탭을 빈칸으로 바꾼 사본 5건). 도구 C 의 ❍ 부호도 못 알아봄.
- 도구 A 점검기는 "2026. 11. 중"의 마침표를 문장 끝으로 세어 "□ 두 문장 이상"이라 함(같은 개요라 세 도구 공통).

### 2-5. rhwp 로 그렸을 때 배치 결함 (앱 내장 편집기·PDF 와 같은 엔진)

rhwp 가 그린 글자 좌표로 셈: 외톨이 줄(앞줄이 찼는데 다음 줄이 본문 폭 25% 미만), 선·글자 겹침, 본문 영역(쪽 높이 − 아래 여백 − 꼬리말 여백) 넘침, 짧게 넘친 꼬리(넘김 줄이 5자 이하).

| | kordoc-ai | 도구 A | 도구 C |
| --- | --- | --- | --- |
| 결함 있는 문서(조판 + 전체 과정) | 14/15 | 4/12 | 1/6 |
| 본문 영역 넘침(쪽번호 자리까지 내려감) | 12건 | 0건 | 0건 |
| 표 바로 다음 줄이 표 아래 선에 걸림 | 3건 | 1건 | 0건 |
| 외톨이 줄 | 17건 | 3건 | 1건(제목) |
| 5자 이하로 넘친 꼬리(전체 과정 9건) | 8건(7문서) | 0건 | (전체 과정 없음) |

- 표 다음 겹침: rhwp 는 떠 있는 표의 아래 바깥 여백을 무시함(여백 1920 → 6000 으로 바꿔도 그대로, 표 뒤에 빈 문단 하나를 넣으면 해결). 도구 A 는 표 뒤에 작은 빈 문단을 넣어 피하고 있음. 도구 C 도 같은 자리가 선에 바짝 붙음.
- 본문 넘침: 쪽번호를 빼도 그대로, 줄간격 180% 를 160% 로 낮추면 사라짐. kordoc 자체 조판(한글 실측 기준)은 같은 문서를 다르게 나눔. 한글에서의 실제 모습은 이번에 확인하지 못함(화면 조작 금지).
- 짧은 꼬리: 리드가 rhwp 줄 정보로 따로 잰 값은 9건 중 25문단(2~5자). 도구 A 는 설명서상 줄 끝을 글자 폭 추정으로 맞춤.

### 2-6. 눈으로 본 판단 (접촉 시트 `bench/compare/out/sheets/`)

- kordoc-ai 보고서: 제목·요약 상자·띠 장 제목·HY견고딕 □·표 머리 음영·쪽번호까지 갖춘 완성형. 다만 `< 소요 예산 >` 같은 표 제목 줄이 왼쪽 보통 글씨로 나오고(도구 A 는 가운데 굵게), 표 뒤 ※ 줄이 표 선에 붙음.
- 도구 A: 장식이 적은 기관 보고서 꼴. 제목 상자·날짜·부서 줄, 표 제목 가운데 굵게, 줄 배치가 깔끔함. 요약 상자·쪽번호 없음.
- 도구 C 기본계획형: 색 띠 제목·리드 상자·파란 장 배너로 가장 잡지 같은 꼴. 긴 제목이 두 줄로 꺾여 "보고" 한 낱말만 남는 경우 있음.
- 전체 과정: kordoc-ai 는 9건 모두 같은 틀로 안정적이나 숫자 나열을 표 대신 ○ 줄로 씀. 도구 A 는 AI 가 만든 표에 빈 열이 생기거나 내용이 붙임으로 빠지는 경우가 있음.

## 3. 나머지 과제

### (a) 기안문

같은 내용(`inputs/gian.json`, 21항목). kordoc-ai 내장 일반기안문 서식(누름틀) 채움: 21/21, 끝 표시, 결재 3명, hwpxlib 열림. 도구 C 원샷 공문: 21/21, 결재 표. kordoc-ai 작성실 기안문 프리셋은 두문·결문 입력이 없어 8/21(엔진은 지원, 앱 연결 안 됨). 비워 둔 선택 칸(경유·협조자 등)은 누름틀 안내 글자가 rhwp 그림에 빨갛게 보임(한글 화면 안내용, 앱은 PDF 내보내기 전에 공백으로 채움).

### (d) 양식 칸 채우기

예제 수요조사서의 값 칸을 비운 빈 양식에 같은 값 7개. kordoc-ai·도구 C 모두 7/7 맞는 칸, 다른 글 그대로, 본문 말고 ZIP 항목 5개 바이트 그대로. 둘 다 hwpxlib 는 거부(빈 양식의 원본 예제가 kordoc 생성본이라 version.xml 없음).

### (e) 옛 HWP → HWPX

kordoc 코퍼스의 HWP 10건과, 같은 문서를 한컴이 HWPX 로 저장한 짝을 정답으로 대조.

## 6. 측정 한계

- 한 대(macOS)에서 잼. 쪽 모습은 rhwp 기준이며 한글의 실제 화면과 다를 수 있음. LibreOffice 변환은 확장 등록 때 GUI 가 떠서 쓰지 않음.
- 그림은 한컴 묶음 글꼴로 그렸으나 크로미움 제약으로 한컴돋움은 다음 글꼴로 대체, HY 글꼴 3종은 다시 저장한 사본, 굵은 꼴 없는 글꼴의 굵게는 획 덧그리기로 흉내 냄. 모든 도구에 같게 적용.
- AI 는 작은 로컬 모델 하나, 메모당 3회. 결과는 실행마다 다름. 도구 A 는 MCP 도구 호출 대신 같은 규칙을 준 JSON 응답으로 흉내 냄.
- 사람 판정은 1명, 도구를 가리지 않은 판정.
- kordoc 표기법 검사는 우리 검사기라 상대 검사기 3종을 같이 씀. 검사기마다 다른 도구의 부호·빈칸 표기를 오독하는 경우가 있어 원인을 따로 적음.
- 도구 B 본 기능은 돌리지 못해 그 도구의 공개 실행 결과(그 저장소 기록)로만 비교.
- 사이드카 번들: 전체 과정은 2026-10-10 21:28 빌드, 나머지는 22:39 빌드(문서 엔진 kordoc 4.21.11 같음). 과제 (c) 회신 공문은 이번 회차에 안 함.
